# 스킬 평가 — 스킬이 만든 것을 채점하기

English: [skill-evals-en.md](skill-evals-en.md) · 설계: [RFC 0005](rfc/0005-rubric-scored-evals-ko.md) · 스키마: [`core/skills/eval/tests/RUBRIC-SCHEMA.md`](../core/skills/eval/tests/RUBRIC-SCHEMA.md)

QABuddy에는 두 종류의 평가가 있습니다. **픽스처**(`/qa-eval`, `tests/fixtures.json`)는 스킬
출력의 *형태*를 검사합니다 — 헤딩이 있는지, 특정 문자열이 없는지 — 그리고 공짜입니다. **루브릭
평가**(`bin/eval.js`)는 *품질*을 검사합니다: 스킬이 대상 모델에서 실제로 실행되고, 별도의
판정자가 스킬 자신의 제약 조건에 대해 산출물을 채점하며, 그 판정은 사람이 보증한 것입니다.
이 문서는 두 번째 종류에 대한 것입니다.

## 한 번의 실행이 하는 일

```bash
node bin/eval.js run test-cases
```

1. **컨트롤 먼저.** 바닥값이 있는 모든 기준에는 `tests/controls/` 아래에 일부러 망가뜨린
   산출물이 있습니다. 판정자가 이를 채점하고, 하나라도 바닥값 이상이면 루브릭이 공허한 것이므로
   러너에 한 푼도 쓰기 전에 작업이 멈춥니다.
2. **러너.** `tests/cases/<id>/` 아래 각 케이스마다 3회: 케이스가 지정한 픽스처 앱 변형을
   띄우고, 케이스의 `input/`을 스크래치 워크스페이스에 복사하고, 헤드리스 프리앰블(질문
   금지, 옵션 A 선택, `features-kb/`·`playwright/`·`.qa-reports/`에만 쓰기)과 함께 대상
   모델에서 `claude -p "/qa-<skill> <args>"`를 실행합니다.
3. **채점.** `check` 기준은 생성된 파일을 grep하고, `process` 기준은 실행 디렉터리와 도구
   호출 스트림을 읽으며, `judge` 기준은 케이스 입력·판정자 전용 노트·산출물·앵커를 담아 Opus
   호출 한 번으로 갑니다 — 스킬의 `SKILL.md`는 절대 보내지 않습니다. 인용된 증거 줄이 없는
   판정 점수는 0입니다.
4. **판정.** 총점 = Σ(가중치 × 점수 / 3) / Σ 가중치. **PASS**는 평균 ≥ 임계값이면서 어느
   실행에서도 바닥값 위반이 없어야 합니다; 아니면 기준과 실행을 지명한 FAIL입니다.
   캘리브레이션되지 않은 루브릭은 `REPORT-ONLY`를 보고하고 절대 게이트하지 않습니다.

출력: `.qa-reports/evals/<skill>/<timestamp>/{report.md, scores.json, eval.log, <case>/run-n/}`.

## 명령

| 명령 | 하는 일 | 비용 |
|---|---|---|
| `run <skill> [--cases a,b] [--runs 3] [--model id] [--eval-budget usd]` | 위의 평가 | test-cases ≈ $3, exploratory ≈ $8 |
| `controls <skill> [--passes 3]` | 컨트롤만 판정 | 몇 센트 |
| `ab <skill> --a <ref> --b <ref> [--cases] [--runs 3]` | 각 ref를 차례로 빌드·설치하고 둘 다 실행해 기준별로 비교 | 실행의 약 2배 |
| `judge <workspace> --skill s --case id` | 기존 산출물 디렉터리를 채점 | 몇 센트 |
| `calibrate <skill> --init` / `calibrate <skill>` | 캘리브레이션 세트 조립 / 판정자와 사람 점수 비교 | 몇 센트 |
| `report <dir>` | `report.md` 재생성 | 무료 |

`ab`는 **전역 QABuddy 설치**(`~/.claude/skills/qa-*`)를 변형마다 교체했다가 이전 심볼릭 링크를
정확히 복원합니다; A/B 중에는 같은 기계에서 QABuddy 스킬을 실행하지 마세요. 같은 명령을
`.github/workflows/skill-eval.yml`로 CI에서 수동 실행할 수 있습니다.

## 보고서 읽는 법

- **기준별** — 모든 실행에 걸친 평균·최소·최대·바닥값 위반. 총점이 아니라 이 표를 읽으세요:
  한 기준에만 영향을 주는 규칙은 한 행만 움직입니다.
- **편차** — 실행 총점의 최대 − 최소. A/B에서 델타가 더 큰 편차보다 크면 회귀 또는 개선이고,
  그보다 작으면 "이 n에서는 구분 불가"입니다. 3회 실행은 큰 효과만 검출하며, 보고서가 그렇게
  말합니다.
- **증거** — 모든 판정 점수는 결정한 줄을 인용합니다. 점수가 이상해 보이면 인용문이 산출물과
  앵커 중 어느 쪽 잘못인지 알려 줍니다.

## 언제 실행하나

- **`/qa-improve`가 대신 실행합니다**(0.8.0): 캘리브레이션된 루브릭을 가진 스킬의 수정은 전달
  전에 기준 ref와 A/B됩니다; 바닥값 위반이나 편차를 넘는 회귀는 전달을 막습니다.
- 캘리브레이션된 스킬, 프리앰블, 그 스킬이 읽는 플레이북 섹션에 대한 **모든 수동 편집** —
  CONTRIBUTING 체크리스트가 PR에 `ab` 표를 요구합니다.
- **모델 업그레이드** — 같은 케이스, 양쪽에 `--model`.
- **플레이북 ablation** — 변형 브랜치 하나와 `ab` 한 번(RFC 0005 §6에 사례 4건).
- **주기적 기준선** — 캘리브레이션된 스킬마다 몇 주에 한 번 `run`하면 러너 드리프트를 잡습니다.

커밋마다는 아닙니다: 전체 실행은 실제 비용과 한 시간의 벤치 시간입니다.

## 캘리브레이션 — 판정자를 신뢰하는 이유

루브릭은 `threshold: null`로 시작하며 보고만 할 수 있습니다. 게이트하려면 캘리브레이션을
통과해야 합니다:

1. `calibrate <skill> --init`이 컨트롤, 평가 실행 워크스페이스, `--extra` 파일로부터
   `tests/calibration/<entry>/`를 조립합니다. 각 엔트리에는 케이스 입력·판정자 노트·산출물·앵커
   — 판정자가 보는 모든 것 — 를 담은 `scoring-sheet.md`가 있습니다.
2. 메인테이너가 모든 엔트리를 **블라인드로** 채점합니다: 판정 기준마다 0–3 하나와
   `acceptable`(동료에게서 이 상태로 받겠는가?)을 `human.json`에. `scored_by`가 `proposed:`로
   시작하는 파일 — 모델의 초안 — 은 절대 집계되지 않습니다.
3. `calibrate <skill>`이 모든 엔트리를 3회 판정하고 보고합니다: 기준별 정확 일치율(게이트 ≥
   0.8), 엔트리별 다수결 바닥값 일치(게이트 1.0), 실제 산출물의 재현성(쌍 일치 ≥ 0.8, 바닥값
   뒤집힘 없음), 제안 임계값 = acceptable로 표시된 평가 실행 엔트리 중 최저 판정 총점.
4. 모든 게이트가 성립할 때만 `threshold`와 `calibration`을 `rubric.json`에 씁니다.

두 파일럿을 통과시킨 규칙: **판정자와 사람이 어긋나면 앵커를 다시 쓰거나 앵커에 비추어 잘못
채점된 엔트리를 고친다; 사람 점수를 판정자 쪽으로 옮기지는 않는다.** 두 파일럿 모두 2–3회의
패스가 필요했습니다. 앵커, 판정자 모델, 인용된 제약 조건이 바뀌면 캘리브레이션이 초기화됩니다.

## 다른 스킬에 루브릭 추가하기

1. `tests/rubric.json` — 스킬의 번호 매긴 제약 조건과 자체 평가 항목에서 도출한 기준(`cites`가
   해석되어야 함), `judge` 기준의 0–3 앵커, must 기준의 바닥값, Opus id인 `judge.model`,
   판정자가 채점할 `artifacts` glob.
2. `tests/cases/<id>/` — 최소 3개: 해피 패스, 얇거나 적대적인 입력, 스킬의 가장 어려운 제약
   조건을 건드리는 것. `judge-notes.md`는 판정자에게 필요한 정답 정보를 담으며 `input/` 아래에
   절대 나타나면 안 됩니다.
3. `tests/controls/` — 바닥값 기준마다 망가진 산출물 하나; `node test.js`가 `check`/`process`
   컨트롤을 실행하고 실패하지 않는 컨트롤을 거부합니다.
4. `node bin/eval.js controls <skill>` — 모든 judge 컨트롤이 바닥값 아래여야 합니다.
5. 산출물 10개를 만들고(실행 3회 + 컨트롤이면 대부분 채워짐), 채점하고, 캘리브레이션합니다.

`node test.js`가 이 모든 것을 구조적으로 검증하며, `CONTRIBUTING`에 체크리스트가 있습니다.
