# RFC 0005 — 루브릭 채점 스킬 평가: 형태가 아니라 성능을 채점하기

**상태:** Accepted — PR1–PR5 빌드 완료, 두 파일럿 모두 캘리브레이션 완료 (2026-09-06) | **저자:** Timothy Han (Claude와 함께) | **작성:** 2026-09-05
**의존:** RFC 0004 (헤드리스 실행, `claude -p`, 재사용 워크플로우) · RFC 0001 (실행 디렉터리, `events.jsonl`, `learnings-log.jsonl`)
**동반 문서:** [0005-rubric-scored-evals-plan.md](0005-rubric-scored-evals-plan.md) — PR별 구현 계획
**번역:** 이 문서는 [영문 원본](0005-rubric-scored-evals.md)의 **비규범 전문 번역**입니다. 두 판이 다르면 영문판이 규범입니다.

## 요약

지금의 `/qa-eval`은 스킬 출력의 **형태**를 검사한다 (`contains "TC-"`, `not_contains "```typescript"`).
simulate 모드는 스킬을 읽은 모델이 스스로 시뮬레이션하고 스스로 채점하므로 순환적이고,
execute 모드는 강하지만 코드 산출 스킬 3개에만 있다. 이 도구로는 세 질문에 답할 수 없다:

1. 플레이북 섹션을 뺐을 때 출력이 **나빠졌는가** (2026-09-05 리뷰가 "ablation 필요"로 남긴 4건).
2. `/qa-improve`의 수정이 스킬을 **더 좋게** 했는가, 아니면 그냥 다르게 했는가.
3. 모델이 바뀌면 스킬이 필요로 하는 컨텍스트가 바뀌는가 (CONTRIBUTING의 Sonnet 피로 전제는 2026-04-11에 쓰였고 Sonnet 5에서 검증된 적이 없다).

이 RFC는 **루브릭 기반 채점**을 더한다. 세 역할을 분리한다: **러너**(대상 모델에서 헤드리스로
스킬 실행, 루브릭을 모름), **판정자**(러너와 **다른 모델** — Opus가 Sonnet 실행을 채점, 결정 15 — 입력·산출물·루브릭만 받고
SKILL.md는 절대 보지 않음), **결정적 검사**(exit code, grep, 로그 — 공짜이고 정확함). 기준은 스킬 자신의
제약·자체 평가 항목에서 나오고 그 줄을 인용해야 한다. 가중 합계 하나로 게이트하지 않는다 —
**must 기준마다 바닥값**이 있고 하나라도 깨지면 FAIL이다. 모든 must 기준은 **네거티브 컨트롤**
(일부러 망가뜨린 산출물)이 바닥 아래로 떨어지는 것을 증명해야 하며, 판정자는 사람이 채점한
산출물 10개와 대조해 **캘리브레이션**되기 전에는 PASS/FAIL을 내지 못한다. 실행은 케이스당 3회,
평균과 편차를 보고한다.

파일럿은 `test-cases`와 `exploratory` (로그에 실행이 가장 많고, 산문 산출, fixture 앱이 둘 다
지원). 첫 결정은 2026-09-05 리뷰가 남긴 ablation 4건이다.

## 1. 문제

`/qa-eval`은 **형태**를 채점한다. 13개 스킬의 픽스처 72개 중 66개가 simulate 모드다: 모델이
`SKILL.md`를 읽고, 실행을 상상하고, `contains "READY"` 같은 문자열을 자신이 상상한 출력에
대조해 검사한다. 6개는 execute 모드(코드 산출 스킬 3개)로 실제로 Playwright를 실행한다 —
동작을 채점하는 픽스처는 이것뿐이다.

이번 주 저장소가 답해야 했지만 답할 수 없었던 세 질문:

| 질문 | 어디서 나왔나 | 지금의 평가가 말해주는 것 |
|---|---|---|
| 플레이북 섹션을 뺐을 때 출력이 나빠졌는가? | 2026-09-05 신선도 리뷰가 후보 4건을 "Sonnet 5에서 ablation 필요"로 남김 (삼중 진술 패턴, `techniques-per-heuristic`, `shift-left#principles`, CONTRIBUTING 피로 전제) | 없음 — 품질을 단언하는 픽스처가 없다 |
| `/qa-improve`의 수정이 스킬을 더 좋게 했는가, 아니면 그냥 다르게 했는가? | `/qa-improve` Phase 4는 형태 단언에 대한 `pass_after ≥ pass_before`로 게이트한다 | 헤딩은 유지하면서 추론을 저하시키는 수정이 통과한다 |
| 모델 업그레이드가 스킬이 필요로 하는 것을 바꾸는가? | CONTRIBUTING: "Sonnet은 지시 피로를 겪는다" — 2026-04-11에 쓰였고 재검증된 적 없음 | 없음 |

인용 로그(RFC 0001)는 어떤 섹션이 *쓰였는지*는 말할 수 있지만, 그 섹션이 없었다면 출력이
나빠졌을지는 말할 수 없다. 그러려면 스킬을 두 번 실행해 품질을 비교해야 하고, 그러려면
러너가 스스로를 채점하는 것이 아닌 품질 점수화 방법이 필요하다.

## 2. 설계

### 2.1 세 역할, 세 컨텍스트

| 역할 | 무엇인가 | 보는 것 | 절대 보지 않는 것 |
|---|---|---|---|
| **러너** | 대상 모델에서 케이스에 대해 헤드리스로 실행되는 스킬 (RFC 0004 `claude -p` 경로; CI에서는 재사용 워크플로우) | 설치된 스킬, 케이스 입력, 앱 | 루브릭, 판정자 노트 |
| **판정자** | 산출물마다 **러너와 다른 모델**로의 별도 호출 한 번 — Opus가 Sonnet 실행을 판정 (결정 15) — 고정 버전, temperature 0 | 케이스 입력, 산출물, 판정자 전용 노트, 루브릭의 `judge` 기준과 앵커 | `SKILL.md`, 러너의 트랜스크립트, 다른 실행의 점수 |
| **검사** | 결정적 단언: 기존 execute 모드 연산자, grep, exit code, 실행 디렉터리(`events.jsonl`, `scratchpad.md`, 실행 파일)에 대한 프로세스 검사 | 실행 산출물 | — |

simulate 모드의 순환성은 한 컨텍스트가 세 역할을 모두 맡는 데서 온다. 이를 분리하는 것이
설계의 전부이고, 나머지는 장부 정리다.

### 2.2 루브릭 — `core/skills/<skill>/tests/rubric.json`

```jsonc
{
  "skill": "test-cases", "skill_version": "0.5.2", "rubric_version": 1,
  "judge": { "model": "claude-opus-5", "prompt": "core/skills/eval/judge.md" },   // never the runner's model (decision 15)
  "threshold": null,                       // set by calibration (§2.6); null = report only, never PASS/FAIL
  "criteria": [
    { "id": "traceability", "kind": "judge", "weight": 3, "floor": 2,
      "cites": { "constraint": 3, "self_check": 1 },
      "statement": "Every AC has at least one test case and every test case names its AC; no orphans, no untested ACs.",
      "anchors": { "0": "ACs without cases and no gap listed", "1": "gaps exist but are not listed as gaps",
                   "2": "complete, one mapping inconsistency", "3": "complete and consistent across cases, mapping and gap list" } },
    { "id": "no-code", "kind": "check", "weight": 1, "floor": 1,
      "cites": { "constraint": 2 },
      "check": { "field": "files:features-kb/**/test-cases/*.md", "op": "not_contains", "value": "```typescript" } },
    { "id": "probed-or-unverified", "kind": "process", "weight": 2, "floor": 1,
      "cites": { "constraint": 7, "self_check": 7 },
      "check": { "field": "run:scratchpad.md", "op": "matches", "value": "^Observed:|\\(unverified\\)" } }
  ]
}
```

- **기준은 스킬 자신의 계약에서 도출된다.** 모든 기준은 `cites`를 가지며, `test.js`가 이를
  `SKILL.md`의 번호 매긴 제약 조건과 자체 평가 항목에 대조해 해석한다. 루브릭은 스킬이
  약속한 적 없는 것을 채점할 수 없고, 제약 조건을 바꾸는 `/qa-improve` 수정은 그 제약을
  인용하는 루브릭을 건드려야 한다.
- **세 종류.** `judge`(앵커로 0–3 채점), `check`(기존 픽스처 연산자, 이진 → 0 또는 3),
  `process`(실행 디렉터리에 대한 연산자: 스킬이 `applied`를 로그했는가, `Observed:` 줄을
  썼는가, `AskUserQuestion`을 호출했는가 — RFC 0004 (f) 패턴의 일반화).
- **앵커가 있는 0–3 척도**, 1–10이 아니다. 세분성보다 재현성; 앵커는 판정자와 사람 사이의
  불일치를 진단 가능하게 만든다.
- **점수** = Σ(가중치 × 점수/3) / Σ 가중치, 0–1 범위. **바닥값**은 기준별·실행별로 검사한다.

### 2.3 케이스 — `core/skills/<skill>/tests/cases/<id>/`

```
cases/
  projects-happy/
    case.json        # { "app": "v1", "port": 4173, "input": "...", "runner_args": "projects --headless" }
    input/           # what the runner gets: ticket/spec text, features-kb files, existing tests
    judge-notes.md   # facts only the judge sees (which existing test is vacuous, where the planted bug is)
```

`judge-notes.md`는 `ANSWER-KEY.md`의 일반화다: `/qa-eval` 제약 7이 이미 평가 대상 스킬에
정답지를 보여주는 것을 금지한다; 같은 규칙이 여기에도 적용되며, `test.js`는 어떤 케이스의
`input/`에도 그 노트의 텍스트가 들어 있지 않은지 검사한다. 케이스는 평가 픽스처 앱(v1 기준선,
v3 심어둔 버그)과 RFC 0004 스크래치 저장소를 재사용한다; Jira 의존 스킬의 케이스는 컨텍스트를
spec 모드 파일로 실어 보낸다.

### 2.4 네거티브 컨트롤 — 평가 자신의 뮤테이션 스모크

`test-suite-verification#mutation-smoke`를 채점자에 적용한 것: 나쁜 산출물에 낮은 점수를
준 적이 없는 루브릭은 검출력이 없다. 바닥값이 있는 모든 기준은 `tests/controls/<criterion>.md`
아래에 망가뜨린 산출물 하나를 함께 배포한다(실제 출력에서 그 한 가지만 망가뜨린 것: 매핑에서
AC 하나를 뺀 것, 코드 블록이 있는 케이스, 파일 경로 없는 "Confirmed"). 평가 작업은 컨트롤을
먼저 판정한다; **바닥값 이상으로 채점된 컨트롤이 있으면 러너 비용을 한 푼도 쓰기 전에
"rubric vacuous: <criterion>"으로 작업이 실패한다.**

### 2.5 샘플링

케이스당 3회 실행. 기준별 평균·최소·최대를 보고하고, 스킬별 판정:

- **PASS**: 총점 평균 ≥ 임계값 **이고** 모든 실행에 걸쳐 바닥값 위반이 0.
- 그 외에는 **FAIL**, 기준과 실행을 지명한다.
- **A/B** (QABuddy ref 둘, 같은 케이스, 같은 모델): 기준별 평균 델타와 양쪽 편차. 더 큰
  편차보다 큰 하락은 회귀; 편차 안의 것은 "n=3에서는 구분 불가"이며 정확히 그렇게 보고한다.

n=3은 큰 효과만 검출한다. 이는 소수점 뒤에 숨기지 않고 모든 보고서에 명시한다.

### 2.6 판정자 캘리브레이션

루브릭은 `threshold: null`로 시작하며 보고만 할 수 있다. 게이트하려면 캘리브레이션되어야 한다:

1. 메인테이너가 루브릭으로 산출물 10개 이상을 손으로 채점한다 — 로그의 실제 출력 더하기
   컨트롤.
2. 판정자가 같은 산출물을 각각 3회 채점한다.
3. 기준별 일치율(정확 점수) ≥ 80 %, 바닥값 결정 100 %, 세 패스에 걸친 판정자 재현성이 총점
   0.1 이내. 아니면 판정자가 아니라 앵커를 고친다.
4. 임계값을 도출하고 — 메인테이너가 acceptable로 표시한 산출물 중 최저 총점 — 캘리브레이션
   날짜·일치율과 함께 `rubric.json`에 기록한다.

판정자 모델, 앵커, 스킬의 제약 조건이 바뀌면 캘리브레이션이 초기화된다.

### 2.7 어디서 실행되나

- **로컬:** `node bin/eval.js run <skill> [--cases a,b] [--runs 3] [--ref <git-ref>]` — 케이스 ×
  실행마다 RFC 0004 헤드리스 호출을 감싸고, 실행 디렉터리와 KB 산출물을
  `.qa-reports/evals/<skill>/<ts>/`에 모으고, 검사를 실행하고, 판정자를 호출하고, `scores.json`과
  `report.md`를 쓴다. `eval.js judge <dir>`는 스킬을 실행하지 않고 기존 산출물 디렉터리를
  채점한다(캘리브레이션, 앵커 변경 후 재채점).
- **CI:** `skill-eval.yml`, `skill`, `ref-a`, `ref-b`, `model`로 수동 디스패치. ref 둘이 ablation
  벤치가 된다. 작업당 비용 상한; 상한에서 작업이 멈추고 부분 결과를 보고한다.
- **모델 귀속:** 모든 `scores.json`은 러너와 판정자 모델을 기록한다. 2026-09-05 리뷰는 일반
  실행 프로파일에 모델 필드가 없음을 발견했다; `eval.js`가 평가에 대해 이를 고치고, 작은
  Akela 변경(`AKELA_MODEL` → `profile.model`)이 모든 실행에 대해 고친다.

### 2.8 기존 평가와의 관계

| 레이어 | 채점 대상 | 비용 | 유지? |
|---|---|---|---|
| `test.js` 구조 검사 | 파일, id, 예산, 루브릭 정형성 | 무료 | 예, 루브릭 검사가 추가됨 |
| simulate 픽스처 | 출력 형태, 자체 채점 | 토큰, 러너 없음 | 케이스 없는 스킬에는 예; 루브릭이 캘리브레이션된 스킬에서는 폐기 |
| execute 픽스처 | 생성된 코드를 실행해서 | 러너 + Playwright | 예 — 코드 스킬의 루브릭에서 바닥값을 가진 `check` 기준이 된다 |
| **루브릭 평가** | 품질, 기준별, 모델 귀속 | 러너 × n + 판정자 | 신규 |

`/qa-improve` Phase 4 3단계는 이렇게 바뀐다: 픽스처가 여전히 통과하고 **그리고**, 변경된
스킬에 캘리브레이션된 루브릭이 있으면 `eval.js` 전/후에 바닥값 위반과 편차 밖의 회귀가 없어야 한다.

## 3. 확정된 결정

| # | 질문 | 결정 | 이유 |
|---|---|---|---|
| 1 | 누가 채점하나? | `SKILL.md`도 트랜스크립트도 절대 보지 않는 별도 판정자 호출 | simulate 모드는 한 컨텍스트가 실행하고 채점해서 순환적이다; 판정자는 절차가 아니라 계약에 대해 산출물을 채점한다 |
| 2 | 기준은 어디서 오나? | 스킬의 번호 매긴 제약 조건과 자체 평가 항목, `test.js`가 인용을 해석 | 루브릭은 스킬이 이미 주장하는 계약이다; 스킬에서 조용히 표류할 수 없다 |
| 3 | 척도 | 서면 앵커가 있는 0–3 | 그 이상의 세분성은 노이즈다; 앵커는 판정자/사람 불일치를 진단 가능하게 만든다 |
| 4 | 게이트 형태 | 임계값 **그리고** 기준별 바닥값 | 가중 합계는 무너진 기준 하나를 숨긴다; RFC 0002 결정 2·11과 같은 논리 |
| 5 | 컨트롤은 선택인가? | 아니오 — 바닥값이 있는 모든 기준이 하나씩 배포하고, 먼저 판정하며, 공허한 루브릭은 작업을 실패시킨다 | `test-suite-verification`: 한 번도 빨간 적 없는 검사는 아무것도 증명하지 않는다 |

첫 패스들이 바꾼 것:

- **§5 (c) 재작성.** 가중치 3 기준에서 앵커 한 단계 뒤집힘은 0–1 총점을 0.143 움직이므로, "총점 0.1 이내"는 세분성에서 실패했다. 규칙은 이제 실제 산출물에서 쌍 일치 ≥ 0.8과 바닥값 뒤집힘 0으로 측정한다; 컨트롤은 분산을 보고하되 검출력만 게이트한다.
- **사람은 `traceability`를 스킬의 제약 3이 읽는 대로 — "테스트되지 않은 AC 없음" — 읽었는데, 앵커는 목록에 오른 갭을 장부 정리로 받아들였다.** 첫 캘리브레이션 불일치로, 판정자 비교 전에 coverage-honesty 컨트롤에서 잡혔다. 결정 14에 따라 재작성: 테스트 케이스가 없는 실제 AC는 목록에 올랐든 아니든 0점, 단 판정자 노트가 커버할 수 없었다고 말하는 경우(플레이스홀더 AC, 앱 없음)는 예외.
- **앵커와 노트가 어긋나면 안 된다.** exploratory 노트는 명세되지 않은 동작을 버그로 등록하면 1점이라고 했는데, 앵커 0은 여전히 그것을 "지어냄"이라 불렀고 판정자는 앵커를 따랐다 (실제 실행 하나에서 0/1/0). 규칙은 이제 앵커 1에 살고 노트는 사실만 진술한다.
- **판정자 노트는 명세되지 않은 동작에 대해 완전해야 한다.** v1-clean 세션은 대소문자 구분 중복 검사를 결함으로 등록했다; 스펙은 이를 결정한 적이 없고 노트도 그렇다고 말하지 않았으므로 판정자는 그 발견을 지어낸 것으로 채점했다. 노트는 이제 명세되지 않은 동작을 나열하고 그런 발견은 0이 아니라 1점(관찰은 맞고 분류가 틀림)으로 채점한다.
- **ko 빌드는 duration을 `소요 시간`으로 표기한다.** `duration-recorded` 검사는 오직 그 이유로 실제 실행 3/3에서 실패했다; 이제 두 표기 모두 받아들인다. 영문 템플릿 기준으로 쓴 검사를 한국어 설치본에 적용한 것은 스킬이 아니라 루브릭의 로케일 버그다.
- **벤치가 드러낸 스킬 발견, `/qa-improve`용:** `test-cases`는 헤드리스 실행에서 도달 가능한 앱의 라이브 프로브를 건너뛰고 대신 상세를 `(unverified)`로 표시했다; 앱 없는 `thin-ticket`은 스크래치패드에 "unreachable" 메모가 없었다; 케이스 문서에 세 실행 중 한 번 펜스 블록이 들어갔다.

**Ablation 집계 (2026-09-05, 판별력 검사 포함 A/B 4건에 $53.89):** n=3에서 편차 규칙을 넘은 ablation은 없었고, 이는 노이즈 많은 스킬에 대한 소규모 n 벤치의 정직한 결과다 — 그리고 모두 일관된 방향을 가진다. 두 결정이 따른다: 삼중 진술을 합치지 않는다 (1), 기법 목록을 유지한다 (2); 전제 하나가 약해졌다: 길이 자체는 Sonnet 5에 해롭지 않았다 (4). Ablation 3은 test-plan 케이스를 기다린다. §5 (f) 충족.

**test-cases 캘리브레이션 완료 (2026-09-06).** Timothy가 엔트리 열 개를 모두 채점했다; 캘리브레이션 패스 3회와 앵커 개정 2회 후 (커버리지 값 없음 = 아무것도 주장하지 않음; 스펙에서 복사한 상세는 관찰 표시가 필요 없음; 아무것도 인정하지 않는 것은 앵커 3; 바닥값 쪽은 패스 다수결로 결정), 일치율은 traceability 1.0, coverage-honesty 1.0, dedup-by-assertion 1.0, prioritization 0.97, observed-or-unverified 0.90; 바닥값이 있는 모든 기준에서 바닥값 일치 1.0; 실제 산출물의 쌍 일치 0.95; **임계값 0.857** (acceptable로 표시된 실제 실행 셋 중 최저 판정 총점). 루브릭은 이제 게이트한다. 캘리브레이션 판정자 총 지출 ≈ $8.

**exploratory 캘리브레이션 완료 (2026-09-06).** 같은 루프, 패스 3회: 앵커 명확화 다섯 건 (별개 시나리오면 충분; 포커스 영역 정산이 없는 보고서는 unexplored-noted 0점; 확인은 "as expected"라 말하고 N/A를 달 수 있음; 결과 표는 차터가 아님)과 점수 수정 열 건, 하나를 빼고 모두 초안 제안에 대한 것. 최종 일치율 (`rubric.json`에 기록된 대로): finding-correctness 0.87, classification 0.90, evidence 0.83, charter-quality 0.90, no-duplicate-scenarios 1.0, unexplored-noted 1.0; 바닥값이 있는 모든 기준에서 바닥값 일치 1.0; 쌍 일치 0.9; **임계값 0.709** (v1-clean 실행, acceptable로 표시된 실제 세션 넷 중 최저). 두 파일럿 루브릭 모두 이제 게이트한다; §5 (b) 충족.

임계값은 각 `rubric.json`에 기록된다; 앵커, 판정자 모델, 인용된 제약 조건이 바뀌면 초기화된다. 파일럿에는 더 이상 `null`로 남는 것이 없다 — 다음 `eval.js run` 판정은 PASS 또는 FAIL이고, `/qa-improve`의 루브릭 게이트(PR5)는 `test-cases`와 `exploratory`에 대해 살아 있다. 레거시 메모: 향후 어떤 루브릭이든 메인테이너가 엔트리 스무 개의 `human.json`을 (채점 시트로부터 블라인드로) 채우고 `eval.js calibrate`가 게이트 (b)와 (c)를 통과하기 전까지 임계값은 `null`로 남는다.

### 첫 실전 게이트 실행 (2026-09-12, PR #87)

`eval.js ab test-cases --a main --b improve/mapping-json-contract`, 18회 실행, ≈ $22, 크래시 한 번 포함 세 시간. 양쪽 평균 0.571 대 임계값 0.857; 양쪽 모두 FAIL; 편차를 넘는 델타 없음. 테스트 대상 변경 — 4단계 불릿 하나 — 은 어느 기준도 인용하지 않는 곳을 건드렸으므로, 이 실행은 그것을 측정할 수 없었다. 실행이 가르친 것과 바뀐 것:

- **thin-ticket은 양봉형이었다(0.00 아니면 0.86).** 여섯 번 중 네 번은 파일을 전혀 쓰지 않았다: 스킬이 채팅에서 NEEDS_CONTEXT로 종료했고, 판정자는 부재를 모든 기준에서 0으로 채점했다 — 옳게. 그 케이스의 캘리브레이션 산출물(2026-09-05, 3/3/3/3/3으로 수용 가능 판정)은 문서와 매핑을 썼었다. 판정자가 아니라 스킬에서 고쳤다: 제약 조건 8, *종료는 메시지가 아니라 파일이다*; `status-block`이 이제 이를 인용한다; 판정자 노트는 두 플레이스홀더 AC를 지명한 케이스 0개 문서가 만점 답이라고 말한다.
- **기준선이 자기 임계값을 통과하지 못한다.** thin-ticket을 걷어내고 나면 `main`의 `coverage-honesty` 1.22와 `probed-app` 1.33이 남는다: 스킬이 확인하지 않은 커버리지를 주장하고 헤드리스 모드에서 앱 프로브를 건너뛴다(ablation 1과 같은 발견). 다음 `/qa-improve` 항목으로 기록; 그것이 들어오기 전까지 test-cases의 절대 판정은 FAIL로 읽히며, 결정 16이 게이트를 상대적으로 만든 이유가 그것이다.
- **결정적 속성은 `check` 기준이다.** PR #87이 고친 속성(모든 매핑이 파싱된다)은 이제 쉼표 빠진 컨트롤을 가진 `artifacts-parse`(`json_valid`, 바닥값 1)다; 프로덕션에서 실패하기 전에 벤치에서 실패했을 것이다.
- **하니스가 취약했다.** 디스크가 차면서 B 아홉 번 중 여덟 번째 뒤에 실행이 죽었고, 심볼릭 링크 복원은 첫 오류에서 멈춰 기계의 모든 QABuddy 스킬을 끊어진 링크로 남겼으며, 워크스페이스는 임시 폴더에 있다가 사라졌다. 이제: 시그널과 복원력 있는 `finally`에서 복원, 락의 스냅숏으로 `ab --restore`, A/B 자신의 디렉터리 아래 변형, 실행마다 `scores.json`과 `ab --resume`.
- **실행 id 키잉**(`activity-<task|branch>-hash`, 한 체크아웃에서 병렬 에이전트가 공유하는 엔진 마커 파일)은 eval이 아니라 Akela 업스트림 항목이다 — eval은 실행마다 워크스페이스를 따로 준다.

## 7. 하지 않을 것

- **execute 모드의 대체가 아니다.** 생성된 코드를 실행하는 것이 가장 강한 채점으로 남는다.
- **13개 스킬 전부가 아니다.** 파일럿 둘; 나머지는 캘리브레이션 대조용 로그된 실행이 있을 때만.
- **스킬 간 리더보드 없음.** 점수는 변형과 모델에 걸쳐 스킬을 자기 자신과 비교한다.
- **점수로 자동 머지 없음.** 평가는 사람의 결정에 정보를 줄 뿐, 결정을 내리지 않는다.
- **LLM이 쓰는 루브릭이나 앵커 없음.** 설정에 대한 RFC 0002 §6과 같은 규칙.
- **프로젝트 수준 루브릭은 아직 없음** (열린 질문 1 참조).
