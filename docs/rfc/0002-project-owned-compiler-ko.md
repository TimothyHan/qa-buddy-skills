# RFC 0002 — 프로젝트 소유 컴파일러 설정

**상태:** Accepted — A–D 빌드 완료 (2026-08-20); E는 게이트 뒤에 유지 | **저자:** Timothy Han (Claude와 함께) | **작성:** 2026-08-19
**의존:** RFC 0001 (PR0–PR6, v0.5.0으로 배포) · **대체:** RFC 0001 §8의 PR7/PR8 프레이밍
**번역:** 이 문서는 [영문 원본](0002-project-owned-compiler.md)의 **비규범 전문 번역**입니다. 두 판이 다르면 영문판이 규범입니다 (RFC 0001 결정 7과 같은 이유 — RFC는 결정 기록입니다).

## 요약

RFC 0001은 지식(레퍼런스 섹션 + 학습)을 실행마다 컴파일하고, 무엇이 쓰였는지 세는 데까지 왔다.
그런데 **한 층이 사용자 것이 아니다**:

| 레이어 | 소유 | 업데이트 후 생존 |
|---|---|---|
| 지식 (`LEARNINGS.md`) | 프로젝트 | ✅ |
| **선택 (어떤 섹션이 어떤 스킬에 가는가)** | **배포 파일의 `qab: scope=`** | ❌ |

2026-08-19에 QABuddy 저장소 안에서 스코프를 정리해 `/qa-qa` 슬라이스를 278줄에서 203줄로 줄였다.
**QABuddy 사용자는 같은 일을 할 수 없다** — 그 파일은 업데이트에 덮어써지고, 컴파일러는
`.qabuddy.json`에서 `learningsPath`·`runsDir`만 읽는다.

이 RFC는 세 가지를 프로젝트 소유로 만든다: **스코프 오버라이드**(바닥값 보장), **프로젝트 소유
레퍼런스 섹션**(팀 방법론), **게이트 리포트**(내 데이터가 점수화를 정당화하는가). 그 결과 RFC 0001의
PR7·PR8은 "QABuddy가 한 번 배포하는 단계"가 아니라 **프로젝트가 자기 측정으로 여는 능력**이 된다.

---

## 1. 문제

RFC 0001 §9.3의 판정("이 프로젝트의 증거로는 점수화가 정당화되지 않는다")에 도달하기까지 필요했던
작업은 전부 **배포되는 파일의 편집**이었다: `maintenance-and-ci`를 `qa` 스코프에서 빼고,
`#not-reproducible`을 두 스킬에 넓히고, 프리앰블의 심각도 척도 사본을 지우는 것.

사용자에게는 그 경로가 없다.

1. **스코프를 고칠 수 없다.** 자기 도메인에 맞지 않는 섹션이 매 실행 슬라이스에 실려도, 포크하거나
   업스트림 PR을 기다리는 것 외에 방법이 없다.
2. **팀 방법론을 컴파일 대상으로 넣을 수 없다.** 학습(`LRN-`)은 "한 사실 + 상태 + 증거 + 수명"이라
   팀의 안정적인 플레이북과 형태가 다르다.
3. **자기 데이터로 점수화를 열 수 없다.** 게이트를 통과할 만한 프로젝트여도 켤 방법이 없고,
   자기 로그가 게이트를 통과하는지 볼 방법도 없다.

**핵심:** QABuddy가 "팀에 맞춰 진화하는 파운데이션"이라면, 진화하는 층에 **선택**도 포함되어야 한다.
지금은 지식만 진화하고 선택은 고정이다.

## 2. 설계

### 2.1 스코프 오버라이드 (프로젝트 수준)

`.qabuddy.json`:

```jsonc
"compiler": {
  "scope": {
    "REF-playbook/maintenance-and-ci#ci-cd-pipeline": { "remove": ["qa"] },
    "REF-playbook/exploratory-heuristics#techniques-per-heuristic": { "add": ["test-cases"] }
  }
}
```

규칙:

- **바닥값: `tier=must`는 제거할 수 없다.** 대상 스킬이 구조적으로 의존하는 섹션을 벗겨낼 `remove`는
  조용히 무시되는 게 아니라 **컴파일 시점에 이름 붙은 오류로 거부**된다. 레일은 레일로 남는다.
- **모르는 id는 거부된다** — 최근접 제안과 함께. `log applied`가 이미 하는 것과 같은 검증이라,
  업스트림의 개명이 조용히 죽은 오버라이드가 아니라 큰 소리의 오류로 드러난다.
- **모든 오버라이드가 매니페스트에 보인다**: 패킹된 섹션은 `via: project-override`를,
  탈락한 섹션은 `reason: project-override`를 얻는다. 슬라이스는 스스로를 설명하는 채로 남는다 —
  섹션이 왜 있고 왜 없는지 항상 볼 수 있다.
- 오버라이드는 코어 스코프 해석 **이후**에 적용되므로, 업스트림이 섹션의 기본 스코프를 바꿔도
  그대로 흘러들어온다.

파일 편집이 아니라 설정인 이유: 배포되는 파일은 업데이트에 교체된다. 프로젝트의 `.qabuddy.json`은
프로젝트와 함께 버전 관리되고, PR로 리뷰 가능하며, 업그레이드에도 살아남는다.

### 2.2 프로젝트 소유 레퍼런스 섹션

```jsonc
"compiler": { "references": ["features-kb/house/*.md"] }
```

- 코어 레퍼런스와 같은 `qab:` 규약(`id`, `scope`, `tier`) — 새로 배울 것이 없다.
- id는 **`PRJ-<file-stem>#<id>`**로 네임스페이스된다 — 배포된 `REF-` id와의 충돌이 불가능하고,
  로그의 인용이 누구 지식이었는지 항상 명확하다.
- `REF-` 섹션과 똑같이 컴파일되고, 인용되고, `stats`가 세고, distill이 리뷰한다.

**왜 그냥 학습을 쓰지 않는가?** 학습은 `Status`/`Scope`/`Evidence`와 수명
(`active → promoted | retired`)을 가진 사실 하나다 — *축적된 증거*다. 팀 플레이북
("우리는 결제를 이렇게 테스트한다")은 어디로도 승격되지 않는 안정적인 저술 방법론이다. 이를
`LEARNINGS.md`에 밀어 넣으면 양쪽이 왜곡된다: distill은 `applied` 카운트가 없다며 계속 은퇴를
제안하고, 학습 파일은 이 프로젝트가 발견한 것의 기록이기를 멈춘다.

### 2.3 게이트 리포트

`node qab.js gate`는 RFC 0001 §9.3을 **이 프로젝트 자신의 로그로** 평가해 출력한다:

- 프로파일과 각각의 outcome — ≥ 2 × ≥ 8 문턱 대비
- 휴면 섹션(`in_slice ≥ N ∧ applied = 0`)과 그 `in_slice`, 스킬별 슬라이스 크기
- 명시적 **eligible / not eligible** 줄과 이유

**리포트는 증거를 모을 뿐 원인을 분류하지 않는다.** 휴면 섹션이 "발화 불가"인지 "다른 곳과
중복"인지 "아직 일어나지 않은 작업을 기다리는 중"인지의 판단은 RFC 0001 §9.3에서 사람의
판단을 필요로 했고 지금도 그렇다. 그래서 리포트는 점수화를 켜기 전에 그 분류를 요청하며 끝난다 —
원인을 추측하는 도구는 0001 판정이 경고한 바로 그 오류를 재현할 것이다.

### 2.4 PR7 / PR8 재정의

점수화(`compiler.scoring: true`)와 자동 상태 변경(`autoStatusChanges: true`)은 코드로 배포되되
**기본 off**이며, `qab.js gate`가 자격 있음을 보고하지 않으면 켜기를 거부한다 — 예외는
메인테이너가 **로그에 결정으로 기록되는** 명시적 오버라이드를 메모와 함께 넘기는 것뿐이다.

게이트는 QABuddy가 한 번 통과하는 마일스톤이기를 멈추고, 각 프로젝트가 스스로 통과하는 것이 된다.

*2026-08-20 빌드 완료 (PR D): RFC 0001 §5대로의 점수화, 바닥값을 가진 프로파일별(`tier=must` ∪
해당 pfp의 최근 3개 실행에서 applied ∪ 모든 학습); pfp의 outcome이 8 미만이면 컴파일은 비점수
유지 — 절대 전역 랭킹이 아니다. `log outcome`이 not-eligible → eligible 게이트 전환을 알려,
프로젝트는 자신의 활동이 게이트를 여는 순간을 알게 된다 (결정 9).*

## 3. 확정된 결정

| # | 질문 | 결정 | 이유 |
|---|---|---|---|
| 1 | 오버라이드 vs 포크 | 파일 편집이 아니라 프로젝트 설정 | 배포 파일은 업데이트에 교체된다; 설정은 프로젝트와 함께 버전 관리되고 리뷰 가능 |
| 2 | 오버라이드가 무엇이든 제거할 수 있나? | **아니오 — `tier=must`는 바닥값** | 레일은 스킬이 구조적으로 의존하는 것을 빼앗기지 않게 존재한다; 설정 버그가 스킬을 조용히 망가뜨려선 안 된다 |
| 3 | 오버라이드의 모르는 id | 최근접 제안과 함께 큰 소리로 거부 | 조용한 no-op 오버라이드는 오류보다 나쁘다: 프로젝트는 설정됐다고 믿는다 |
| 4 | 프로젝트 섹션의 네임스페이스 | `PRJ-<stem>#<id>` | 인용은 출처가 명확해야 한다; 배포 id와 충돌 없음 |
| 5 | 프로젝트 섹션 vs 학습 | 둘 다, 역할 구분 | 학습은 수명을 가진 축적된 증거; 플레이북은 저술되고 안정적 (§2.2) |
| 6 | `gate`가 휴면 원인을 분류하나? | **아니오 — 증거를 모으고 묻는다** | RFC 0001 §9.3이 보여줬듯 원인 분류에는 판단이 필요하다; 추측하는 도구는 자기가 경고하는 실수를 반복한다 |
| 7 | 점수화 기본값 | off, 그리고 자격 없이는 켜기를 거부 | 0001의 판정은 얇고 좁은 데이터 위의 점수화가 능동적으로 해롭다는 것 |
| 8 | `gate`는 어디 사는가? (구 열린 질문 2) | **`qab.js gate`** (PR C, 2026-08-20) | 두 로그에 대한 결정적 읽기 전용 리포트는 `stats` 옆이 자리다; distill 모드였다면 같은 데이터를 LLM으로 다시 읽었을 것. distill은 그 출력을 인용하면 된다 |
| 9 | 프로젝트는 게이트가 열린 걸 어떻게 아나? | **`log outcome`이 not-eligible → eligible 전환을 알린다**; 프리앰블이 SDT에게 전달하고 묻는다 | QABuddy는 실행 중에만 살아 있고, outcome만이 문턱을 넘길 수 있는 이벤트다 — 풀 전용 리포트는 그 순간을 놓친다. 정확히 한 번 울리고, 켜는 것은 사람 몫 |
| 10 | 점수화 노브 | **설정이 아니라 상수** — `min_samples` 8, 오디션은 10번째 실행마다, 최근 창 3; 설정은 `scoring` + `budget_lines`뿐 | §6 non-goal: 조정 가능한 노브는 모든 설치본의 동작을 설명 불가능하게 만든다 |
| 11 | 학습도 점수화되나? | **아니오 — 학습은 바닥값** | 프로젝트 자신의 교정은 예산에 밀려 떨어져선 안 된다 |
| 12 | 오디션 선택 | 결정적 — pfp의 10번째 닫힌 실행마다, RNG 없음 | 같은 로그 상태는 같은 슬라이스로 컴파일되어야 한다; 재현성이 매니페스트를 증거로 만든다 |
| 13 | 얇은 프로파일 데이터 | **비점수 컴파일**, 절대 전역 폴백 아님 | §9.3 판정: "절대 전역 `applied` 랭킹이 아니다" — 얇은 데이터가 전역으로 폴백하면 측정된 바로 그 오류를 반복한다 |

## 5. 측정

- 프로젝트들이 실제로 오버라이드를 설정하는가, 그 결과 슬라이스가 줄어드는가?
- 어떤 프로젝트의 `gate`가 eligible을 보고하는 날이 오는가 — 그리고 점수화가 픽스처 퇴행 없이
  적용 비율을 개선하는가 (RFC 0001 §9.3 킬 기준은 여전히 적용)?
- 프로젝트 소유 섹션이 인용되는가, 아니면 팀들은 전부 `LEARNINGS.md`에 두는가?

## 6. 하지 않을 것

- **프로젝트별 점수화 알고리즘 없음.** 하나의 알고리즘, 하나의 플래그. 조정 가능한 노브는 모든
  설치본의 동작을 설명 불가능하게 만든다.
- **LLM이 쓰는 설정 없음.** `/qa-setup`은 제안할 수 있다; `.qabuddy.json`은 사람이 쓴다.
- **`tier=must` 오버라이드 없음** (결정 2).
- **도구의 원인 분류 없음** (결정 6).
- 오버라이드는 스킬 안까지 들어가지 않는다 — 절차는 사람이 쓴 채로 (RFC 0001 부록 B).

## 7. 열린 질문

1. `/qa-improve` distill이 어떤 프로젝트에서 `in_slice ≥ N ∧ applied = 0`을 보면, 오늘 학습의
   은퇴를 제안하듯 스코프 오버라이드를 *제안*해야 하는가?
2. 프로젝트 섹션은 인용되기 전에 자기 eval 픽스처가 필요한가, 아니면 매니페스트로 추적성이
   충분한가?

("`gate`는 어디 사는가"는 결정 8로 해소됐다: `qab.js gate`.)
